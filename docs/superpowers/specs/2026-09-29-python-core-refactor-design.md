# Python 核心重构与 V1.0 完整交付设计草案

日期：2026-09-29
状态：Superseded（已被替代）。当前目标以 [V1.0 架构手册](../../ARCHITECTURE-V1.md)为准；作者产品需求已移除，数据标注已加入正式范围。下文保留为历史检查与方案演进记录，不作为新的实施基线。
范围：实际运行入口、回合流程、模型调用、内容加载、状态与审计存储，以及完整 V1.0 的能力差距与交付顺序（第 10 节）。
验证：现有离线 architecture-check 已通过；未运行真实模型、桌面试玩或 Python 全套测试。

## 1. 已确认的目标与默认约束

用户明确选择：让 Python Agent 后端成为核心，桌面端只做界面。

目标架构中，Python 独立承担战役、规则、事件、Agent 编排、上下文、记忆、内容读取和审计。Electron 负责窗口、界面、文件选择、系统凭据保管、本地后端的启动与通信。

本草案默认：
- 首轮仍为本地单用户产品；Python 服务随桌面运行，不建设远程多租户服务。
- 保留现有玩法、公开信息边界、角色创建、战役恢复、检查点、分支和审计能力。
- 已有桌面存档需可迁移；开发验证使用生成的临时数据或明确指定的存档副本，不扫描真实战役。
- 旧浏览器独立运行模式退出正式产品；以后浏览器预览与 Electron 均连接同一个 Python 后端。
- 单项迁移保持已确认行为；V1.0 缺失能力在整体里程碑中补齐（见第 10 节），不把迁移完成当作项目终点。
- 目录名在职责迁移完成前保持稳定，优先复用 services/ai-api，避免先全仓改路径。

成功标准：
1. 不启动 Electron，也能通过 Python API 完成创建角色、行动、规则判定、状态提交和读取结果。
2. 界面只消费展示数据与操作状态，不执行权威规则、事件重放、模型调用或数据库写入。
3. 相同初始状态、内容版本、随机种子和行动，在新旧内核中保留已确认的规则与玩家可观察结果；内部结构可通过版本适配演进，已知缺陷不作为必须复制的行为。
4. 一个运行中的战役只有一个权威写入方。
5. 新增模型任务有明确的输入、输出、权限、预算、失败行为和审计归属。

## 2. 现状与证据

### 2.1 正式桌面端与浏览器路径并存

- electron/src/renderer/session.ts 共 1527 行。
- 第 575 行根据 tryDesktopApi 判断路径；第 587 行提交给桌面服务。
- 第 731 行起的浏览器路径自行执行 playTurn，随后写入事件和记忆。
- 第 809 行调用 runAfterCommitLive；第 871 行调用 keeperNarrate。
- electron/src/main/services/turns.ts 是桌面端独立的回合编排入口。
- electron/src/renderer/store/repo.ts 与 main/persist 分别提供两套存储实现。

影响：修改一次自由行动、记忆处理或恢复行为时，容易只修到其中一条路径。

边界说明：不能由此推断当前桌面端存在双重落库。session.ts 第 710 行明确说明桌面分支的推导仅用于调试展示，不再次保存。

### 2.2 回合服务集中承担过多职责

electron/src/main/services/turns.ts 共 1013 行，包含：
- 请求、角色与版本检查，重复命令处理；
- 路由、自由行动、规则处理和提交；
- 模型配置、调用与用量记录；
- 派生记忆与剧情状态保存；
- 叙事生成、增量推送、最终回复保存；
- 审计和角色卡应用。

影响：持久化、模型与桌面通信细节交织，迁移或添加任务需要理解整个服务。
这属于职责集中问题，不能只靠按行数拆成多个工具文件解决。

### 2.3 模型接入和规则 Agent 有多处实现

- 正式桌面回合：core/keeper/keeper.ts → core/keeper/client.ts → 模型接口。
- TypeScript 能力与评测链：core/ai/lc/chains.ts、provider.ts、tools.ts。
- Python：services/ai-api/app/gateway.py、rules.py。

源码搜索中，TypeScript 的 narrateTurn / resolveWithRules 的外部调用集中在 electron/scripts/bench.ts；没有找到正式桌面回合直接调用 /v1/agent/rules 或 /v1/retrieve。

影响：评测链与正式玩家链不一致，不能直接把一条链的结果解释为另一条链的产品效果。
模型配置可能允许桌面把兼容聊天请求发往网关；这仍不代表 Python 已经拥有战役编排和状态。

### 2.4 Python 目前是网关，不是完整游戏后端

main.py 暴露 health、retrieve、chat/completions 和 agent/rules，没有完整的战役、角色、回合、检查点和审计业务 API。

Python rules.py 的 skill_check 是“骰点 + 属性 >= 难度”；正式游戏 engine/rules.ts 使用百分骰、普通/困难/极难阈值以及大成功/大失败。

Python 已有与 TypeScript 对齐的 UTF-16 FNV-1a / Mulberry32 随机数实现及测试向量，应复用。随机数一致不等于游戏规则和状态转换已经一致。

### 2.5 内容模块混合领域定义、环境适配与全局状态

electron/src/core/engine/pack.ts 共 709 行，同时负责：
- Schema、内容校验和索引；
- localStorage 中的活动内容包选择；
- Bun、Electron 文件读取与 Vite glob；
- 模块加载时初始化全局 pack / packIndex。

影响：纯规则代码导入内容模块就带入运行环境和全局内容选择。多战役不同内容包、隔离测试和 Python 迁移都会受此牵连。

### 2.6 接口定义重复，现有架构检查未约束依赖边界

- shared/api.ts 定义桌面协议；renderer/desktop.ts 再次定义 DesktopCampaign、DesktopTurnView 等。
- renderer/desktop-play.ts 仍调用 replay(initialState(), events)。
- 多个 UI 组件直接读取 pack / packIndex 或执行规则辅助函数。
- architecture-check.ts 检验确定性、派生任务和状态指纹，不检查“界面禁止引用规则和模型实现”等依赖规则。

这些位置应逐步改为消费后端合同与公开展示数据，不应一次删除全部类型或测试。

## 3. 方案比较

| 方案 | 作用 | 代价与限制 |
| --- | --- | --- |
| 仅拆 TypeScript 大文件 | 短期降低阅读成本 | 仍由桌面掌握业务，不满足已确认方向 |
| 一次重写全部 Python 后端并切换 | 最终边界直接 | 难以定位行为差异，存档、规则、叙事和审计同时承担风险 |
| 逐段迁移能力，完成兼容后切换写入方 | 每段可对照旧实现验证，最终只保留 Python 核心 | 迁移期间保留受控的旧实现与对照测试；必须明确退出条件 |

推荐第三种。先把行为和边界迁对，再整理名称和删除旧实现。

## 4. 目标职责

保持现有仓库顶层布局，按实际迁移逐步形成以下结构，不提前创建空目录：

~~~text
electron/src/
  main/                     窗口、后端进程、文件与凭据桥
  preload/                  最小桌面桥
  renderer/
    api/                    Python API 客户端与合同类型
    session/                界面会话、操作订阅与交互状态
    ui/                     展示组件

services/ai-api/app/
  main.py                   应用装配
  api/                      HTTP 输入输出、公开 DTO、操作事件
  application/              回合、战役、角色、恢复和审计用例
  domain/                   规则、事件、状态、随机数、内容模型
  agents/                   GM、上下文、工具、输出校验、后台任务
  infrastructure/           SQLite、内容文件、模型和检索适配

tools/lora/、tools/embedding/ 保持训练工具独立
~~~

依赖约束：
- api 调用 application；不直接执行 SQL、拼 Prompt 或判定规则。
- application 组织 domain、Agent 与持久化，拥有权威状态提交入口。
- domain 不依赖 FastAPI、LangChain、数据库、浏览器或 Electron。
- agents 只产生受限的请求、候选和叙事；模型不能直接写权威状态。
- infrastructure 实现具体的模型、存储与检索访问，由应用装配处注入。
- 前端类型来源于后端 API 合同；不再手写多套等价接口。
- 后端返回公开状态及调试投影，前端不为了展示而重新运行规则或后台任务。
- 内容包加载显式按战役绑定的 ID 与版本进行，避免进程级活动 pack 单例。

Agent 编排先保持现有任务和 LangChain 接入能力。是否引入新的图编排框架另行由真实的分支、恢复与人工交互需求决定，不作为本轮前置条件。

## 5. 一条权威回合链路

~~~text
界面提交行动（commandId、branchId、expectedStateVersion）
  → Python 记录/取得 operation，处理重复请求
  → 加载战役及绑定内容，检查角色与版本
  → 确定性快路径或 GM 结构化行动理解
  → 校验候选，执行确定性规则
  → 事务内再次检查版本并提交事件与状态版本
  → 基于已提交结果生成叙事，校验可见性与事实一致性
  → 保存最终回复并发布操作状态
  → 执行受版本约束的记忆/剧情派生任务
~~~

关键行为：
- 查询、澄清和无效行动沿用已有语义，不统一强行变成消耗回合的提交。
- 模型调用期间不持有数据库写事务；提交时必须重新检查版本。
- 同一 commandId 的重试关联原 operation，不重复掷骰、重复提交。
- 已提交结果后的叙事失败只重试叙事，不重新执行行动。
- 未通过公开信息守卫的文本不能作为玩家可见增量发送；保留现有秘密泄露回归约束。
- 后台结果带所依据的状态版本；过期结果不得覆盖新状态，也不能确认新事实。
- 调试界面读取后端实际执行记录，不由前端补跑一条“看起来相同”的流程。
- 迁移先保持桌面当前实际启用的任务。不能因浏览器路径存在 runAfterCommitLive，就默认在新桌面版本启用全部后台模型调用。

传输建议：HTTP 提交/查询，加服务端事件流发送操作进展。断线后按 operationId 读取持久化结果，事件流不是最终事实来源。首个后端纵向切片可先轮询，最终桌面切换前补齐既有的进度与完成交互。

本地启动：Electron 启动隐藏的 Python 服务，等待健康检查就绪后开放操作；界面显示可理解的启动或失败状态。后端绑定回环地址，桌面桥持有本次启动的访问凭据。系统密钥保管可继续使用 safeStorage，模型密钥只交付后端，不进入渲染层、日志或公开 API 返回值。

## 6. 存储与兼容

最终由 Python 独占战役写入。首轮优先适配现有 SQLite 结构和事件格式，不同时更换数据库系统。

需保留并验证：
- campaign、branch、turn、command、operation、事件顺序和版本的对应关系；
- 角色档案、内容绑定与版本、检查点及派生分支；
- 最终叙事、近轮对话、恢复摘要；
- 反馈、诊断、复核、用途资格、导出批次及脱敏规则。

开发期间：
- 旧 TypeScript 实现仅作为参考与对照测试运行在独立临时数据库。
- Python 模式不得同时注册旧 TurnService 等写入入口。
- 不把新后端指向仍被旧桌面占用的战役数据库。
- 迁移命令在明确副本上验证格式与版本；失败保持源数据不变。
- 在未确定向后兼容前，不允许旧程序打开已升级格式；回退使用保留的旧副本。
- 浏览器 WASM 数据与桌面 SQLite 格式不同，不能假定统一直接读；保留旧导出入口，浏览器数据转换另列验收范围。

内容文件最终从桌面打包实现中解耦；先通过显式内容根路径复用现有 JSON，职责迁移完成后再移动资源目录。

## 7. 分阶段交付与最小验证

### 阶段 0：冻结迁移合同

工作：
- 从现有行为提取固定输入、事件和状态样例，以及公开的请求/结果字段。
- 标明正式游戏流程与 Bench 实验流程的差异。
- 记录必须保留的幂等、版本、秘密可见性、回滚与审计语义。

验证：
- 复用已通过的 architecture-check 基线。
- 需要新增跨语言样例时，先在旧实现验证输出，再作为 Python 验收数据。
- 不通过手工填写“期望正确结果”掩盖现有语义。

### 阶段 1：Python 确定性领域核心

工作：
- 复用已有随机数实现；补齐正式百分骰规则。
- 迁移状态、事件应用、内容模型、条件触发、内核校验与重放。
- 内容模型显式传入，不依赖桌面环境。
- 先覆盖寄宿公寓固定流程，再覆盖雾港角色与调查约束。

验证：
- TS/Python 同输入的骰点、检定等级、规范化事件和最终状态一致。
- 保留无效行动/旧版本不消耗判定等语义。
- 哈希比较需先固定对象序列化、字符串和数值口径；不能只拿语言默认 JSON 比字节。
- 本阶段不切换桌面、不打开真实存档。

### 阶段 2：Python 完整回合服务

工作：
- 迁移战役、角色与持久化用例，完成统一回合入口。
- 迁移 GM 路由/叙事、上下文、守卫和派生任务。
- 迁移恢复、检查点、审计反馈/复核/导出。
- 原 ChatGateway 保留为模型适配能力；通用骰子演示接口不充当正式游戏规则。
- 建立公开 DTO、operation 查询与状态事件。

验证：
- 在临时 SQLite 与固定模型响应下完成创建→行动→提交→叙事→恢复。
- 检查重复请求、版本竞争、模型失败、过期后台结果和秘密内容守卫。
- 现有备份格式的副本导入/导出保持必要字段与语义。
- 审计工作流与导出资格、脱敏规则保持兼容。
- 独立于 Electron 运行后端测试。

### 阶段 3：薄桌面切换

工作：
- 将桌面业务调用改接 Python API；Electron main 仅保留桌面职责。
- session.ts 分离为界面状态和后端操作订阅，删除其正式运行中的领域执行职责。
- UI 使用公开状态、角色、内容和审计投影。
- 浏览器预览连接同一后端，退出独立 WASM 游戏引擎路径。
- 切换前必须补齐目前桌面已提供的能力，避免“主流程能跑”但恢复/复核不可用。

验证：
- 从空白临时战役完成角色创建、一次确定性行动、一次自由行动、恢复及一次反馈复核。
- 关闭再启动后能继续；后端不可用时界面有明确状态。
- 本地后端健康、退出与临时数据库隔离正常。
- 依赖检查禁止 renderer 引入旧 keeper/ai/engine 运行时代码；允许生成的合同类型和纯展示格式化。

### 阶段 4：退出旧实现和整理入口

工作：
- 在调用方切换且等价验证通过后，删除被迁移替代的 TS 实现、重复存储和不再使用的依赖。
- 未覆盖的旧能力保留清楚的兼容入口，不能直接归为死代码删除。
- 评测改为调用实际 Python 回合/Agent 服务，避免继续维护另一套产品逻辑。
- 更新唯一的当前架构入口；历史设计保留并标明历史状态。
- 最后处理顶层目录命名、内容资源搬迁和 Windows 打包。

验证：
- 无正式产品调用引用旧业务入口。
- 最小相关测试与合同检查通过；仅在影响公共接口时扩大检查。
- 当前架构文档与实际调用路径一致。
- 不主动发布、覆盖旧安装包或修改用户真实存档。

第一轮实施建议先完成第 10 节 M0 中与核心相关的范围约束，再覆盖阶段 0–1：交付与已确认行为等价、能够承载 V1.0 支持范围的 Python 领域核心。其局部验收不需要真实模型、GPU、训练或 UI 大改；通过后继续迁移完整回合服务并推进 V1.0，不以首轮通过作为项目完成。

## 8. 防止后续 AI 修改重新扩散

后续实施时将以下规则写入对应目录的 AGENTS.md，并用最小依赖检查支撑：
- 新功能先写明属于哪个既有用例；不能为同一流程另起第二入口。
- 玩家权威状态只能由后端应用用例提交。
- 模型调用只能经过后端统一适配层，Prompt 与输出合同归对应任务。
- 新能力必须覆盖正式调用路径，不能只在演示或评测脚本可用。
- 不默认新增 Manager、Registry、全局单例、通用 Agent 平台或另一套协议类型。
- 迁移一个能力时，写明替代对象、兼容方式、验收条件和旧入口退出条件。
- 测试证明行为和跨层约束，不用“文件变小”作为完成标准。

这些规则属于建议实施项，本次尚未创建 AGENTS.md 或修改代码。

## 10. 新增最终目标：完整 V1.0 交付

本节根据用户在架构检查后新增的要求补充：项目最终交付完整 V1.0，而非只完成代码整理或 Python 迁移。
前述阶段 0–4 是架构迁移工作包；迁移通过不能作为 V1.0 完成结论。

### 10.1 兼容性结论

Python 核心与薄桌面端能够承载现有产品路线图的 V1.0。产品原则中的 GM 唯一前台、AI 提议/程序提交、权威事件、可追溯记忆和非破坏性恢复，都不要求业务必须驻留 Electron。

需要修改的是旧技术设计中“Electron 主进程拥有业务与数据库”的部署归属。这些职责转给 Python，事实权威、提交顺序、信息可见性和恢复语义继续保留。

原方案存在三项需要修正的限制：
1. “迁移现有能力”没有覆盖尚未实现的 V1.0 产品能力。
2. 按现有 Demo 数据模型逐字段照搬，可能继续固化 hp/san、单一角色位置、特定锁与调查动作等表达边界。
3. 只按旧行为验收，无法验证外部内容、长期战役和作者使用流程。

因此采用同一仓库内的受控核心重建：复用已验证规则、内容与测试，重新组织 Python 应用/Agent/存储边界，并以 V1.0 支持范围校准领域模型。无需新建一个失去历史与证据的独立项目，也不把所有旧代码逐行翻译。

### 10.2 “完整 V1.0”的产品范围

暂按 docs/00-product/roadmap.md 的现有 V1.0 定义：
- 普通玩家独立安装、配置、导入内容、创建、游玩、保存、恢复并完成战役。
- 建议行动与自由输入均可用，规则、状态和叙事一致，失败保留真实后果。
- 支持声明范围内的普通文字卡、轻量冒险与正式 Scenario Pack，并解释能力差异。
- 内容作者能够制作、检查、试玩并发布正式包；现有实现设计允许以模板、文档和 CLI 交付，不要求可视化编辑器。
- 在明确的目标战役长度内保持关键状态、记忆和剧情因果，提供可测量的成本和时延边界。
- 模型可按能力要求替换，存档不依赖某个模型。
- 回滚、分支、备份、故障恢复及玩家/作者文档完整。

沿用现有非目标：多人实时联机、真人 GM 工作台、所有规则/模型/文字卡变体的完全兼容、大量自主 NPC 社会模拟。
Windows x64、具体内容格式、规则和 Provider 支持矩阵需在 V1.0 范围基线中明确。现有 docs/05-implementation-design 文档仍是 Draft，不将所有历史实现细节自动当成已批准的承诺；与新部署归属冲突的部分必须更新。

“目标战役长度”、叙事质量通过线、支持硬件及模型条件尚未在本次检查中形成统一且可执行的发布标准。应在相应实现开始前定义测量协议并冻结验收口径，不能在发布时临时降低标准。
现有测试草案中的“100 回合无无界内存增长”只是耐久测试要求，不等价于长期叙事与记忆能力已经验收。

### 10.3 从当前实现到 V1.0 的差距

| 能力 | 已有可复用内容 | V1.0 尚需完成或验证 |
| --- | --- | --- |
| 回合与规则 | 确定性内核、事件重放、百分骰、角色与调查测试 | Python 权威后端、独立于固定 Demo 的内容/规则绑定、完整玩家流程 |
| 内容导入 | JSON/PNG 文字卡解析、预览、候选确认；Scenario 打包/检查脚本 | 安装内容库、版本绑定、导入后独立开局、分级能力提示、内容升级与错误处理 |
| 作者流程 | 两个示例内容包及现有打包/校验素材 | 作者按文档制作一个新包，校验、导入、试玩并分发，无需修改引擎代码 |
| 长期记忆与剧情 | 事件来源、记忆游标、派生结构及可选模型任务 | 正式后端接通完整流程；长战役、模型失败、过期结果和中断恢复验证 |
| 模型接入与评测 | Python 网关、规则证据、TS 模型守卫与评测资产 | 正式运行与评测使用同一应用能力；对认证 Provider 做真实回合验收 |
| 恢复与审计 | 桌面备份/分支/检查点，反馈/复核/脱敏导出 | Python 完整迁移、旧格式副本转换、跨重启恢复、用户可理解的操作流程 |
| Windows 交付 | Electron 构建与解包产物流程 | Python 运行时随包交付、干净环境安装、启动/退出、升级/回退及发布资料 |

这里的“尚需验证”不等于认定已有代码错误；本次没有进行完整产品验收。

### 10.4 复用与重建的界线

保留并迁移：
- 已确认的规则结果、随机数语义、提交与恢复不变量；
- 现有剧本、角色卡样例、测试样例、隐私规则和训练留档；
- 可继续消费后端展示数据的 UI 组件及桌面能力。

重建或合并：
- Python 的回合应用服务与 Agent 编排入口；
- 混合 UI/业务的 session 流程、重复的模型接入和协议定义；
- 全局 pack 单例与运行环境混用；
- 阻碍 V1.0 内容能力的领域/持久化表达。

兼容不要求内部数据库、类结构或新事件字段永远与 Demo 相同。旧事件和存档通过显式版本与适配读取；比较的是规范化后的规则、事实与玩家可观察结果。
已发现的缺陷不能为了对照一致而在新实现中复制。任何有意改变的玩法语义单列需求与测试，不混进“等价迁移”结果。

### 10.5 调整后的交付顺序

| 里程碑 | 用户可见的交付结果 | 验收重点 |
| --- | --- | --- |
| M0：V1.0 范围与迁移基线 | 一份统一范围表，每项标明实现/迁移/验证状态、验收证据和依赖 | 产品承诺一致；桌面/Python 权责明确；历史草案冲突有处理结论 |
| M1：新核心接管现有可玩版本 | Python 独立运行，桌面可完成已有完整短剧本并保存恢复 | 对应前文迁移阶段 0–3；迁移规则与数据时先检查 V1.0 表达需求，避免锁死 Demo |
| M2：内容与作者流程完整 | 用户导入声明支持的文字卡、轻量内容和正式包后能开始；作者能制作并试玩新包 | 解析成功不等于可游玩；同一 validator 用于作者工具和运行时导入 |
| M3：长期运行与模型适配达标 | 在冻结的目标长度和模型条件下持续游玩、切换合格模型、处理中断与失败 | 实际游戏链的质量/时延/成本、记忆溯源、剧情因果、恢复及审计证据 |
| M4：V1.0 发布验收 | 独立可安装的 Windows 完整版本、玩家与作者文档、支持矩阵和已知边界 | 干净环境、真实模型、外部试玩、升级/备份恢复、发布阻断问题清零 |

每个里程碑按完整用户流程组织，完成一个可验收结果后再推进下一项；不并行维护“旧桌面新增功能”和“新 Python 同功能”两条长期产品线。
架构迁移中的阶段 4 清理按能力退出逐步执行，不等待 V1.0 最后一天才删除全部重复实现。

第一轮仍可以从确定性核心开始，但在写模型和数据结构前先完成 M0 对相关能力的约束；首轮结束只是阶段交付，整个项目目标继续指向 M4。

### 10.6 正式版本的完成判定

V1.0 完成需要产品功能、实际模型效果和分发验收三类证据同时成立：
- 自动测试证明确定性、合同、事务、信息可见性与恢复行为。
- 真实模型评测与外部试玩证明自由行动、叙事、记忆和长期体验达到冻结标准。
- 干净 Windows 环境证明安装、随包 Python、启动、保存、重启、升级与恢复可用。

现有发布草案还包含签名、更新渠道、SBOM、许可证及至少一个云 Provider 和 Ollama 的真实验收。这些条目需要在 M0 中明确为采用的发布门槛或经用户认可调整的范围，不能因迁移完成就略过，也不能把未签名的开发演示包直接标成满足 stable 发布要求。

签名凭据、发布渠道、真实模型与外部试玩等依赖应提前登记。缺少其中某项时，准确标记未通过的发布门槛，继续完成不受影响的工作，不宣称完整 V1.0 已交付。

本次只修订目标、差距与交付路径；未启动 M0 实施计划编写、Python 迁移、业务功能开发或正式发布。
