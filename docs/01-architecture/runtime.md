# Runtime 与回合协调

## 定位

Runtime 是一次游戏操作的确定性协调边界。Coordinator 负责推进回合阶段、调用所需组件、收集候选、组织校验与原子提交，并把已提交结果交给 GM 叙事。它不理解剧情含义，不代替规则或领域模块作决定。

## 回合状态

每个回合绑定 `turn_id`、`branch_id`、起始 `state_version`、玩家输入和处理状态。处理状态至少区分接收、澄清、准备上下文、裁定、待提交、已提交、待叙事、完成和失败，避免重试时重复执行已完成阶段。

## 标准流程

1. 接收输入并绑定当前分支与状态版本。
2. Turn Router 选择纯叙事、简单行动、复杂机械行动或澄清路径。
3. Context Broker 构建该任务允许使用的信息包。
4. 必要时由 GM 输出行动意图；程序确定规则、目标和适用约束。
5. Rule Engine 与 RNG Service 生成可复现的裁定记录。
6. 领域模块和 Scenario Runtime 根据裁定产生或检查状态变化候选。
7. Validator 检查 schema、来源、权限、前后值、版本和领域不变量。
8. State Store 与 Event System 原子提交状态、事件和裁定记录。
9. GM 根据同一 `turn_id` 和已提交 `state_version` 生成正式叙事。
10. 发布后台任务，刷新派生视图与 Active Context，并交出下一行动权。

澄清回合不得提前掷骰或提交变化。纯角色扮演回合若不改变权威状态，可以只记录必要的交互事件。

## 候选与提交

Runtime 可以同时收集 GM、Director、Memory 和领域 Analyzer 的候选，但候选必须标明来源、依据事件、目标实体和所基于的状态版本。候选之间冲突时不按 AI 优先级直接选择，而由领域约束、规则结果和剧本条件决定；仍无法确定时进入澄清或异常处理。

原子提交包含本回合全部相互依赖的状态变化与事件。任何一项校验失败都不得留下部分提交。

## 并发、版本与幂等

- 提交前再次确认分支和状态版本；版本过期时重新读取并重新评估候选。
- 同一 `turn_id` 的同一提交请求只能成功一次。
- RNG 结果绑定回合、骰式和种子，重试不得重新生成。
- 已提交后的叙事重试只读取提交结果，不重新进入裁定阶段。
- 切换分支、读档或回滚会取消仍绑定旧时间线的未提交任务。

## 失败处理

- 上下文非必需信息缺失时降级继续；必需信息缺失时暂停对应操作。
- AI 调用失败时保留当前阶段和输入，可安全重试或采用确定性路径。
- 校验失败时拒绝候选并记录原因，不修改权威状态。
- 原子提交失败时整个事务失败；恢复后使用同一回合标识重试。
- 提交后 GM 失败时显示可恢复状态并重试叙事，不撤销已经发生的事实。
- 无法判定玩家重要意图时请求澄清，不擅自选择会改变风险或目标的解释。

## 禁止职责

Runtime 不负责生成叙事、判断语义相关性、拥有领域事实、决定规则内容或修改 Scenario Canon。它只保证正确的组件在正确阶段使用同一版本的数据，并使结果以可追溯、原子且可恢复的方式提交。
