# 实现计划

把 [05-里程碑.md](05-里程碑.md) 落到本仓库上。共用同一条提交边界的工单只能串行，其余的可以并行。

## 0. 现状与差距

| 部分 | 现在是什么样 | 需要变成什么样 |
| --- | --- | --- |
| 外壳 | Tauri 2、Vite、React 19 | 保持不动 |
| 模型 | 一条系统提示，加上一批**会写库**的工具 | 改成主持人契约，写入只发生在运行时 |
| 检定 | `src/lib/check.ts` 里的百分骰和二十面骰 | 改为加载规则资料包，种子与 `turn_id` 绑定 |
| 道具 | 静态的 `src/data/items.ts` 加一个查阅工具 | 改成状态里的道具实例，动作归领域管 |
| 房间 | 只存在于手册里 | 变成权威数据，保证一个东西只在一处 |
| 剧情 | 手册里的标记和开关 | 引入 `StoryProgress`，条件在提交之后判定 |
| 记忆 | `notes` 加对话表 `message` | 事件记录才是存档，对话只负责显示 |
| 人物卡 | 偏 D&D 的 `Character`（护甲等级、职业、六维） | 改成调查员：理智、技能；护甲等级不再是核心字段 |
| 提示词 | 「只用 5e SRD，不要自称官方 D&D」 | 由资料包决定，试玩就是寄宿公寓 |
| 遭遇／战斗 | 有一张遭遇表 | 对试玩不关键，搁到 V0.x |
| SRD 检索 | 属于额外能力 | 试玩阶段不做 |

在提交循环真正立起来之前，不要加导演、记忆模型和人设卡导入。

## W1 — 权威内核（M0）

**结果：** 程序能提交一个回合，并且能重放。

1. 新建 `src/engine/`，定义 `entity_id`、`branch_id`、`turn_id`、`state_version` 和事件信封。
2. 做 SQLite 迁移：
   - `branch`、`turn`、`event`、`rule_decision`
   - 房间、道具实例、调查员、NPC、线索、剧情标记、开关各自建表（三个房间的规模用表就够，不必整包塞文档）
3. 实现 `Runtime.commit`：版本检查、全有或全无、按 `turn_id` 幂等。
4. 掷骰时记录种子，重试不重新掷。
5. 把 `check.ts` 收到 `rules.resolve(intent, state, seed)` 后面。
6. 写无界面测试：脚本化地跑「开书桌锁」的失败和成功，哈希必须稳定。

**停在哪：** 聊天界面仍然可以用旧工具，但测试已经证明新内核成立。

---

## W2 — 回合路由与主持人契约（M0）

**结果：** 模型再也写不了事实。

1. 定义 Zod 联合类型：`clarification`｜`context_request`｜`action_intent`｜`narration`。
2. 替换掉那些会写库的工具（`update_character`、战斗相关的变更、被当成权威用的 `write_note`）：
   - 读取一律经过上下文调度（道具、房间、人物卡的视图）
   - 1 级和 2 级由运行时自己落实
   - 主持人只在 3 级输出 `action_intent`
3. 定义回合的各个阶段：接收 → 路由 →（澄清）→ 裁定 → 提交 → 叙述。
4. 界面加一条处理提示：「正在检定书桌锁」，但不报成败。
5. 如果叙述把仍然锁着的书桌写成打开了，就拒绝这段叙述，按同一版本重试。

**实验记录：** 在只有三个房间的地图上，2 级快匹配到底值不值得（「进书房」「取走账本」这类多半是值得的）。

---

## W3 — 把寄宿公寓做成资料包（M1）

**结果：** 手册里的东西能真正玩起来，而不只是一张图解。

1. 把手册里的房间、道具、动作、剧情标记和条件写成 JSON，放进 `src/data/packs/boarding-house/`。
2. 实现剧本运行时：每次提交之后判定条件，需要立即触发的就放进同一个事务。
3. 实现可见性：玩家视图与守秘人视图（道具的 `keeper` 字段已经有雏形）。
4. 开团流程：预组的林晚，出生点为 `loc.hall`，免掉完整的车卡回。
5. 这份资料包里不再出现 5e 专用的措辞。

**停在哪：** 测试能走通「门厅 → 书房 → 开锁失败 → 再开锁成功 → 取走账本 → 阅读 → 理智降到 60 → 剧情标记完成」这一条路。

---

## W4 — 跑团桌（M1）

**结果：** 试玩的人不会觉得这只是套了层皮的聊天窗口。

1. 聚会页面：叙述列居中，人物卡和房间小地图常驻。
2. 建议行动的芯片来自上一条 `narration.suggested_actions`。
3. 已有的检定卡改为绑定 `rule_decision`，而不是绑定模型写的散文。
4. 可以展开的部分：背包、线索、剧情标记、事件记录。
5. 存档和读档都走检查点加事件，明确拒绝「把聊天记录导出来当存档」。
6. 把导演和提示词藏起来，调试路由等以后再说。

到这里做一轮试玩。如果大家记住的还是「那个对话框」，说明桌子没做完。

---

## W5 — 可分发的表面（M2）

1. 首次启动：选供应商、测连通性、创建战役。
2. 设置页面已经有了，补上能力说明和错误文案。
3. 人设卡导入（常见的 Markdown 和 JSON），能力标记为「人设卡」。
4. 资料包格式，配上 `bun run pack:lint`。
5. 用 `tauri build` 出 macOS 包，简短的玩家说明可以放在手册里。
6. 模型失败时：给出提示并允许重试叙述，已经成功的提交不回滚。

---

## W6 — 记忆与导演（M2 末尾接触，正经做在 M3）

必须排在 W1–W4 之后。

1. 记忆：批量整理，并且**引用事件编号**，不删除原始事件。
2. 导演：做一张触发表（线索丢失、NPC 警戒、剧情停滞），`director_proposal` 交给剧本运行时。
3. 临时上下文：当前房间加背包加未完成的剧情标记，读档时重建。
4. 分支与回滚的界面（除非试玩阶段强烈要求，否则放到 M3）。

## 建议的推进顺序

```
W1 内核 ──► W2 路由／主持人 ──► W3 资料包 ──► W4 跑团桌 ──► 试玩 = Demo
                                                    │
                                                    ▼
                                          W5 分发表面 = V0.1
                                                    │
                                                    ▼
                                          W6 导演／记忆 = V0.x
```

两个人做：一人负责 W1 和 W3（数据与规则），另一人等类型定下来之后做 W2 和 W4（模型与桌面）。

一个人做：W1 → W2 → W3 → W4，在试玩的退出条件满足之前不碰 W5 和 W6。

## 头两周（按一个人算）

**第一周**

- 引擎的类型定义，以及 `event` 和 `turn` 两张表
- 把开锁检定迁进内核，配一个固定种子的测试
- 禁止主持人传入 `roll` 和 `ok`（工具模式里已经限制，运行时再强制一次）

**第二周**

- 房间占用，以及道具实例的移动与拒绝
- 条件联动：书桌打开之后，账本才可以取走
- 让一条聚会路径走新的提交流程，旧界面先凑合着用

之后打磨 W4，再做试玩。

## 风险

| 风险 | 对策 |
| --- | --- |
| 模型不守契约 | 用 Zod 直接丢弃，非法对象不产生任何副作用 |
| 快路径误判 | 保守处理，只匹配房间内唯一的那个动词 |
| 把聊天记录当存档 | 读档只读事件 |
| 范围膨胀（战斗、SRD、多人） | 一律搁置，试玩就只有三个房间 |
| 5e 的残留撞上克苏鲁演示 | 由资料包来决定提示词和人物卡 |
| 把整张道具总表塞进提示词 | 交给上下文调度：只给当前房间、背包和可做的动作 |

---

## 每个改动的完成定义

- 新增的提交路径都有测试
- 不新增任何会写库的主持人工具
- 机械性行动无论被接受还是被拒绝，都要写事件
- 领域不变量变了，就同步改手册或者本目录里的需求
