## W1 — 权威内核（M0）

**结果：** 程序能提交一个回合，并且能重放。

1. 新建 `src/engine/`，定义 `entity_id`、`branch_id`、`turn_id`、`state_version` 和事件信封。
2. 做 SQLite 迁移：
   - `branch`、`turn`、`event`、`rule_decision`
   - 房间、道具实例、调查员、NPC、线索、剧情标记、开关各自建表（三个房间的规模用表就够，不必整包塞文档）
3. 实现 `Runtime.commit`：版本检查、全有或全无、按 `turn_id` 幂等。
4. 掷骰时记录种子，重试不重新掷。
5. 把 `check.ts` 收到 `rules.resolve(intent, state, seed)` 后面。
6. 写无界面测试：脚本化地跑「开书桌锁」的失败和成功，哈希必须稳定。

**停在哪：** 聊天界面仍然可以用旧工具，但测试已经证明新内核成立。

---

## W2 — 回合路由与主持人契约（M0）

**结果：** 模型再也写不了事实。

1. 定义 Zod 联合类型：`clarification`｜`context_request`｜`action_intent`｜`narration`。
2. 替换掉那些会写库的工具（`update_character`、战斗相关的变更、被当成权威用的 `write_note`）：
   - 读取一律经过上下文调度（道具、房间、人物卡的视图）
   - 1 级和 2 级由运行时自己落实
   - 主持人只在 3 级输出 `action_intent`
3. 定义回合的各个阶段：接收 → 路由 →（澄清）→ 裁定 → 提交 → 叙述。
4. 界面加一条处理提示：「正在检定书桌锁」，但不报成败。
5. 如果叙述把仍然锁着的书桌写成打开了，就拒绝这段叙述，按同一版本重试。

**实验记录：** 在只有三个房间的地图上，2 级快匹配到底值不值得（「进书房」「取走账本」这类多半是值得的）。

---

## W3 — 把寄宿公寓做成资料包（M1）

**结果：** 手册里的东西能真正玩起来，而不只是一张图解。

1. 把手册里的房间、道具、动作、剧情标记和条件写成 JSON，放进 `src/data/packs/boarding-house/`。
2. 实现剧本运行时：每次提交之后判定条件，需要立即触发的就放进同一个事务。
3. 实现可见性：玩家视图与守秘人视图（道具的 `keeper` 字段已经有雏形）。
4. 开团流程：预组的林晚，出生点为 `loc.hall`，免掉完整的车卡回。
5. 这份资料包里不再出现 5e 专用的措辞。

**停在哪：** 测试能走通「门厅 → 书房 → 开锁失败 → 再开锁成功 → 取走账本 → 阅读 → 理智降到 60 → 剧情标记完成」这一条路。

## W4 — 跑团桌（M1）

**结果：** 试玩的人不会觉得这只是套了层皮的聊天窗口。

1. 聚会页面：叙述列居中，人物卡和房间小地图常驻。
2. 建议行动的芯片来自上一条 `narration.suggested_actions`。
3. 已有的检定卡改为绑定 `rule_decision`，而不是绑定模型写的散文。
4. 可以展开的部分：背包、线索、剧情标记、事件记录。
5. 存档和读档都走检查点加事件，明确拒绝「把聊天记录导出来当存档」。
6. 把导演和提示词藏起来，调试路由等以后再说。

到这里做一轮试玩。如果大家记住的还是「那个对话框」，说明桌子没做完。

## W0 — 外壳与权威边界（已完成）

**已定：Electron。** 不再讨论 Tauri。代码在 `electron/`。

1. Main／Preload／sandbox／contextIsolation／单实例。
2. `window.desktopApi`：`app`、`campaign`、`settings`（含密钥）、`turn`、`timeline`、`operation`。
3. V1 DDL 在 `electron/sql/`。`bun run persist:check` 覆盖迁移、事件不可变、回合提交、订阅回放、密钥落盘不含明文。
4. `turn:submitAction` 在主进程：`playTurn` 提交事实，再 `keeperNarrate`（关掉模型则用模板），写入 `turns`／`events`／`rule_decisions`／`narrations`。同一 `commandId` 幂等。
5. `operation.subscribe` 只推 `operation.status`、`narration.delta`、`narration.completed`、`campaign.changed`。有 `desktopApi` 时 Renderer **不**调用 `keeperNarrate`。
6. 密钥走 `CredentialStore` + safeStorage；Renderer 没有 `getSecret`。
7. 旧壳 `src/lib/tools.ts` 写库工具已停用。
8. `bun run content:pack` 把八个 JSON 打成 `.scenario-pack`（`content:check` 拒 zipslip／哈希不符）。

**停在哪（已达成）：** 金样哈希 `b6506aeb`；Electron 里行动走 `desktopApi.turn.submitAction`；主进程落事实；Renderer 只收 Result 和叙述 delta。

W5 切片已接上：设置页写 `provider_instances`／`model_profiles`／`task_routes`；人设卡确认写入 `sheet_applied`；`bun run package:win` 打 Windows x64。首次启动向导、代码签名、Markdown 人设仍未做。

## W5 — 可分发的表面（M2）

1. 首次启动：选供应商、测连通性、创建战役。
2. 设置页面对齐 V1 的 `provider_instances`／`model_profiles`／`task_routes`。
3. 人设卡导入（常见的 Markdown 和 JSON），能力标记为「人设卡」。
   **现状：** `demo/src/cards/` 读 SillyTavern V1／V2／V3 JSON 和 PNG。自动车数值标 `generated`。用户确认后提交 `sheet_applied`，写入当前战役 hp／san／技能／名字，不改资料包预组定义。`bun run card:check`。还没有 Markdown 人设、升级为轻量冒险。
4. 资料包校验走 content CLI：`validate`／`pack`／`inspect`。
5. 按 [18-release-compatibility](../docs/05-implementation-design/18-release-compatibility.md) 出 Windows x64 包；macOS 开发流不当验收。
6. 模型失败时：给出提示并允许重试叙述，已经成功的提交不回滚。

## W6 — 记忆与导演（M2 末尾接触，正经做在 M3）

必须排在 W0 之后。规格对齐 [11-ai-orchestrator](../docs/05-implementation-design/11-ai-orchestrator.md) 与 [13-context-memory](../docs/05-implementation-design/13-context-memory.md)。

1. 记忆：批量整理，并且**引用事件编号**，不删除原始事件（V1：`memory_entries` + FTS5）。
   **现状：** 提交后确定性 extract 写入 `memory_entries`／`memory_cursors`。Keeper 开启时 `memory.extract`／`consolidate` 可走模型，失败保留程序结果。尚无 FTS5。主持人选项「调试后台任务」可画出 extract/consolidate，默认关。
2. 导演：Story Monitor 旗标 + Frontier 落盘；`directorDue` 时才调 `director.analyze_progress`。机会是候选，不改节点。调试面板同时画出 Frontier 与 Monitor。
3. 临时上下文：当前房间加背包加未完成的剧情标记，读档时重建。调试面板画出 current/preparing 与 retention。
4. 分支与回滚的界面 Demo 已经有了；桌面要走 `timeline:`／`campaign:` IPC，接到 V1 `checkpoints`。

## 风险

| 风险 | 对策 |
| --- | --- |
| 模型不守契约 | 用 Zod 直接丢弃，非法对象不产生任何副作用 |
| 快路径误判 | 保守处理，只匹配房间内唯一的那个动词 |
| 把聊天记录当存档 | 读档只读事件 |
| 范围膨胀（战斗、SRD、多人） | 一律搁置，试玩就只有三个房间 |
| 5e 的残留撞上克苏鲁演示 | 由资料包来决定提示词和人物卡 |
| 把整张道具总表塞进提示词 | 交给上下文调度：只给当前房间、背包和可做的动作 |

---

## 每个改动的完成定义

- 新增的提交路径都有测试
- 不新增任何会写库的主持人工具
- 机械性行动无论被接受还是被拒绝，都要写事件
- 领域不变量变了，就同步改手册或者本目录里的需求
